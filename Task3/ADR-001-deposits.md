### Название задачи:
ADR-001. Заявки на депозиты и накопительные счета онлайн.

### Автор:
Артур (ArtyrKa1300).

### Дата:
25.10.2026.

MVP — через 6 месяцев, с ручной обработкой в АБС. Автоматическое открытие — цель на год. Требования: [FURPS+](../Task2/FURPS.md).

### Функциональные требования

| № | Действующие лица или системы | Use Case | Описание |
|---|---|---|---|
| UC1 | Бэк-офисы, АБС, адаптер, Kafka, сервис депозитов | Обновить ставки | 1. Сотрудники рассчитывают и согласуют ставку. 2. АБС сохраняет утверждённую версию. 3. Адаптер передаёт её через Kafka. 4. Сервис депозитов обновляет копию. |
| UC2 | Клиент, сайт, сервис депозитов, кол-центр, фронт-офис | Подать заявку с сайта | 1. Клиент просматривает ставки и оставляет Ф. И. О./телефон. 2. Сервис сохраняет обращение и передаёт его кол-центру через Kafka. 3. Менеджер звонит. 4. Новый клиент приходит в отделение на идентификацию. |
| UC3 | Клиент, интернет-банк, сервис депозитов | Посмотреть условия | 1. Клиент входит в интернет-банк. 2. Сервис проверяет его доступ. 3. Показывает общие и персональные ставки. |
| UC4 | Клиент, интернет-банк, сервисы депозитов и подтверждений | Подать заявку в интернет-банке | 1. Клиент выбирает продукт, свой счёт и сумму. 2. Получает и вводит СМС-код. 3. Сервис проверяет код, сохраняет заявку и передаёт её через Kafka. 4. Клиент видит номер заявки. |
| UC5 | Адаптер, АБС, бэк-офис, сервис уведомлений | Подтвердить ставку | 1. Адаптер передаёт заявку в АБС. 2. Менеджер подтверждает условия. 3. Через Kafka обновляется статус, клиент получает СМС. Если условия изменились, клиент подтверждает их повторно. |
| UC6 | Бэк-офис, АБС, сервисы депозитов и уведомлений | Открыть депозит | 1. После согласия клиента менеджер открывает депозит в АБС. 2. АБС проверяет счёт и средства. 3. Событие открытия передаётся через Kafka. 4. Клиент видит результат и получает СМС. |
| UC7 | Клиент, интернет-банк, сервис депозитов | Проверить статус | 1. Клиент открывает свои заявки. 2. Сервис возвращает статус. 3. Пока АБС недоступна, заявка остаётся в ожидании. |

### Решение

Диаграммы: [контекст](context.drawio) ([SVG](context.svg)), [контейнеры](containers.drawio) ([SVG](containers.svg)). В контейнерах раскрыты интернет-банк и АБС.

| Компонент | Ответственность |
|---|---|
| Интернет-банк, ASP.NET MVC | Вход и новые экраны каталога, заявки и статусов. |
| Сервис депозитов, Java + MS SQL | Хранит копию ставок, обращения, заявки и статусы. |
| Сервис подтверждений и уведомлений, Java + MS SQL | Проверяет СМС-коды и отправляет уведомления через существующий шлюз. |
| Адаптер АБС, Java | Передаёт команды и события между Kafka и процедурами АБС с ограничением нагрузки. |
| АБС, Delphi + Oracle/PL-SQL | Хранит утверждённые ставки, обрабатывает заявки и открывает счета/договоры. |
| Kafka | Передаёт заявки, ставки, статусы, обращения и уведомления. |
| Сайт и система кол-центра | Сайт принимает обращения, операторы получают их и связываются с клиентами. |

Java выбрана из-за имеющихся специалистов, MS SQL и Oracle уже используются в банке.

**Основной поток:** интернет-банк → сервис депозитов → Kafka → адаптер → АБС. Ставки и статусы возвращаются через Kafka. Сайт получает общий каталог и передаёт обращения через сервис депозитов. Старый монолит общается с новыми сервисами по HTTPS, без прямого подключения к Kafka.

Сервис депозитов читает ставки из своей БД. Благодаря этому каждый просмотр каталога не нагружает Oracle. Персональные ставки доступны только соответствующему клиенту.

Заявка и запись для отправки сохраняются вместе — это outbox. Если отправка прервётся, её можно повторить. АБС проверяет уникальный номер заявки, чтобы не открыть депозит дважды. Адаптер вызывает только выделенные процедуры АБС.

СМС-код связан с клиентом и условиями заявки. Об изменении ставки и фактическом открытии приходят разные уведомления. Для нового онлайн-процесса отправкой управляет новый сервис, чтобы не дублировать СМС из АБС.

**Отказоустойчивость:** несколько экземпляров приложений за балансировщиком, резервирование БД и Kafka, переключение между ЦОД. Для Kafka предусматривается резервный кластер; после сбоя заявки восстанавливаются из сохранённых записей и обрабатываются без дублей. Параметры репликации и время переключения проверяются до запуска. Один резервный ЦОД сам по себе не гарантирует 99,9%.

До разработки нужно проверить расширение интернет-банка без изменения ядра, передачу клиентской авторизации и правила СМС-подтверждения. После пилота за 6 месяцев запускается ручной MVP; затем автоматизируются проверки и открытие без бэк-офиса.

### Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Всё в старом монолите с прямым доступом к Oracle | Увеличивает нагрузку и зависимость от подрядчика. |
| Синхронный API к АБС на каждый запрос | Сбой или замедление АБС влияет на онлайн-канал. |
| Полностью заменить АБС и интернет-банк | Слишком большой объём для MVP. |

### Недостатки, ограничения, риски

- Ставки и статусы обновляются с задержкой.
- Бэк-офис может не успевать обрабатывать поток заявок.
- Kafka и новые сервисы требуют сопровождения.
- Возможность расширения платформы и резервирования нужно проверить с командами.
- Новый клиент с сайта всё ещё должен прийти в отделение.
